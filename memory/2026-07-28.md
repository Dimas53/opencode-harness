# Session 2026-07-28 — agent-e2e: zsh parsing, protocol bypass

## Workarounds

### zsh parse error on `&& while` compound command
- `cd ... && while ...; do ...; done` breaks in zsh — "parse error near `while'"
- `while` is a reserved word, not a command — after `&&` parser expects simple command
- Fix: extract retry loop into `scripts/run-playwright-verify.sh` standalone script, call as `bash script.sh` (single command, no compound syntax)
- Relevant: all agent-e2e bash blocks must avoid `&&` chaining with compound commands

### Agent silently skipped loading agent-e2e.md
- fix-ui step 3.4 said "load agent-e2e as verify gate" — worded as advice, not command
- Agent loaded agent-fix-ui.md, went to step 3, read file, and started `npx playwright test` directly without ever opening agent-e2e.md
- Fix: MANDATORY gate with explicit prohibition: "NEVER call npx playwright test directly, all execution through agent-e2e.md retry-guard"

### run-playwright-verify.sh placement
- First put in `global/scripts/` — wrong, should be `scripts/` (which is symlinked to `~/.opencode-harness/scripts/`)
- `install.sh` creates `~/.opencode-harness` as symlink to repo root, so `scripts/` is auto-available

### "Next?" rule bypassed by agent (general pattern)
- Agent visibly reads "After each finding: ask Next?" but skips it — rationalizes as "user already confirmed progress, no need to ask"
- Fix: merge verify output and "Next?" into one template block. Agent cannot show verify result without outputting `> Next? (y/n/stop)` and waiting for answer before `mark [x]`.
- General principle: text-only confirmation steps are unreliable. Attach them to a preceding action that the agent MUST perform (verify gate, file write, etc.).

### Nuxt server routes not directly testable with vitest
- `server/api/*.ts` uses auto-imported `defineEventHandler` from h3/Nuxt — vitest can't resolve it without setup
- Workaround: `tests/unit/setup.ts` with `vi.stubGlobal('defineEventHandler', ...)` and configure vitest.config.ts with `setupFiles`
- Alternative: add `export` to individual pure functions in the server route, but this changes the module API
- Better long-term: extract pure validation functions into `utils/` module with no server dependencies

### `export` added for testability — acceptable side effect
- agent-fix.md says "Scope per finding: only this file". Adding `export` to an internal function IS in the same file.
- No harm — tree-shaking removes unused exports in production builds.
- Not worth a protocol change; document as accepted practice.
