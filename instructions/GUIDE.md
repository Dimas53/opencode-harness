# OpenCode Harness — Guide

---

## 1. What Is This

The harness is a portable, pre-configured development environment for AI-assisted coding with OpenCode.
Think of it as the difference between an AI chat bot and an AI engineer.

Without a harness, the model only generates text. It doesn't know your project structure,
doesn't remember past decisions, doesn't check for security issues, and doesn't follow
a repeatable process.

The harness adds:

- **Rules** — AGENTS.md files that define how the agent behaves, what it must check,
  what it must never do without asking
- **Context** — documentation files (`PROGRESS.md`, `roadmap.md`, `ARCHITECTURE.md`)
  that give the agent project memory between sessions
- **Tools** — MCP servers that let the agent read files, run git commands, query databases,
  launch browsers, and fetch documentation
- **Skills** — reusable instruction sets for specific tasks (debugging, security review,
  UI engineering, test writing)
- **Process** — Session Start → Work → Definition of Done → Commit → Push → Session End

The goal: one developer, any machine, single command. Clone the repo, run `make setup`,
and get a fully configured AI agent that documents changes, checks security, runs tests,
and follows a repeatable workflow — without writing rules from scratch.

### How it started

The harness was extracted from a real production project (ItoCook — Nuxt 4 + Directus + PostgreSQL).
Every rule in it exists because a mistake was made, a vulnerability was found, or a session
went off track. The rules are battle-tested, not theoretical.

## 2. Two-Layer System (global vs project AGENTS.md)

The harness uses two AGENTS.md files that work together. One is global (applies to every project),
the other is per-project (overrides where needed).

### Global AGENTS.md (`~/.config/opencode/AGENTS.md`)

Installed by `make setup`. Contains universal rules that apply to any project:

| Section | What it covers |
|---------|---------------|
| Behavior | Plan before changes, confirm before commit, never push without asking |
| Language rules | Chat in Russian, English only for code/docs |
| Safety Gates | 13 actions that require explicit user confirmation |
| Safe actions | File creation, doc updates — no permission needed |
| CSS / Layout | Flexbox/grid, no inline styles, tap feedback |
| Code style | TypeScript strict, conventional commits, PEP8, PSR-12 |
| Skills loading | 62 skills with trigger-based auto-loading |
| Session Start | Mandatory 8-step sequence at every session beginning |
| Definition of Done | 6-step checklist before saying "done" |
| Documentation Session | Trigger + script for updating docs |
| Session End Protocol | Runs after git push |
| External projects | Restricted mode for client work |

### Project AGENTS.md (`project/AGENTS.md`)

Generated by `make init` or `make init-adopt`. Contains only project-specific rules:

| Section | What it covers |
|---------|---------------|
| Stack Skills | Which skills to load every session (e.g., nuxt, vue, tailwind) |
| Framework Structure | Nuxt 4, Symfony, or other framework conventions |
| Project File Map | Where source files, components, pages live |
| Task Context | Which doc to read for which task |
| Project DoD | Architecture file mapping specific to this project |
| Git Workflow | Commit conventions, branch strategy |
| MCP Servers | Which servers this project needs |
| Framework Gotchas | Known issues with this specific stack |
| UI Rules | Design tokens, icon library |
| Docs Update Matrix | Who updates which file and when |

### Conflict resolution

When a rule exists in both files — **the project file wins**.
Global rules provide the baseline. Project rules add or override for specific needs.
For example, the global DoD checks tests and PROGRESS.md. The project DoD maps
architectural changes to the correct docs.

## 3. Skills — What They Are and How They Work

Skills are reusable instruction files stored in `~/.config/opencode/skills/`.
Each skill is a directory with a `SKILL.md` file that teaches the agent how to handle
a specific type of task.

### How skills load

Skills load **automatically by trigger**. You don't need to tell the agent which skill
to use. The global AGENTS.md defines trigger rules:

```
Debugging / Error Fix
Triggers: "not working", "error", "bug", "why", "broken", error in logs
→ loads: debugging-and-error-recovery, diagnose, systematic-debugging

Security / Auth / Infrastructure
Triggers: auth, login, token, .env, nginx, Docker, deploy
→ loads: security skill
```

Before every task, the agent:
1. Reads your request
2. Matches it against triggers
3. Loads matching skills
4. Follows the skill's instructions

### Skill sources

| Source | Count | Install method |
|--------|-------|---------------|
| Vendored (harness repo) | ~70 | Copied by `make setup` from `global/skills/` |
| find-skills ecosystem | 6 | Installed on demand, tracked in `~/.agents/.skill-lock.json` |

### How to add a new skill

```bash
# From the find-skills ecosystem — discover and install
# Use the find-skills skill

# Manually: create a directory in ~/.config/opencode/skills/your-skill/
# with a SKILL.md file. The agent will discover it on next session.
```

### The `harness-init` skill

This is the orchestrator skill for project initialization. It:
1. Detects which scenario applies (new project / adopt / analyze-only)
2. Confirms with the user
3. Delegates to the correct agent-skill:
   - `agent-new-project` — interview + full docs generation
   - `agent-adopt` — analyze codebase first, then generate docs
   - `agent-analyze` — deep analysis, audit report only, no file modifications

harness-init itself does NOT run interviews or generate files — each agent-skill
has its own skill stack and workflow.

## 3.5 Choosing a Model

Different tasks need different models. Recommended setup via OpenRouter:

| Task | Model | Why |
|------|-------|-----|
| Routine fixes, small changes | `deepseek/deepseek-v4-flash:free` | Fast, free, good enough |
| Architecture, complex refactoring | `google/gemini-2.5-pro` | Best reasoning |
| Large codebase analysis | `google/gemini-2.5-flash` | 1M context window |
| Complex reasoning, algorithms | `deepseek/deepseek-v4-pro` | Strong reasoning |
| Best overall quality | `anthropic/claude-sonnet-4-6` | Most reliable |

> Tip: Use free models for exploration and quick questions. Switch to paid only when
> the task is complex enough to justify it. RTK saves 80-90% on terminal output —
> the real cost is in your prompts and responses, not command output.

## 3.7 Starting a Project — Shortcuts

The primary way to initialize any project is via shortcuts inside OpenCode:

| Type | What happens |
|------|-------------|
| `new` | Loads agent-new-project — interview + full doc generation |
`adopt` | Loads agent-adopt — codebase analysis + docs |
| `analyze` | Loads agent-analyze — full project audit, no file changes |
| `analyze <path>` | Same, focused on a specific file or folder (e.g. `analyze pages/Dashboard.vue`) |
| `update-harness` | Pulls latest harness updates, applies globally (requires `make link` once) |
| `sync-templates` | Checks for new template files missing in current project, copies with confirmation |

These shortcuts work from any directory inside an open OpenCode session.
No make commands needed — just open OpenCode and type the shortcut.

Fallback if shortcuts don't trigger:
```bash
cd ~/path/to/opencode-harness && make init PROJECT=$(pwd)
```

## 4. How to Start a Session

Every session begins with the command:

```
Start
```

That's it. A single word. The agent then runs a mandatory 7-step sequence:

1. **pwd + git log** — `git log --oneline -10`
2. **Load global skill + task‑specific context** — reads `using-agent-skills/SKILL.md` (filesystem or built-in), then checks `docs/skills-cheatsheet.md` for skills matching your request's triggers
3. **Read PROGRESS.md** — compare git log with progress status; fix if out of sync
4. **Read roadmap.md** — current phase and next tasks
5. **Read MEMORY.md** and `memory/YYYY-MM-DD.md` if they exist (today or yesterday)
6. **Read HARNESS.md** if it exists — apply project constraints and risk levels
7. **Report** — outputs a session brief:

```
Session initialized. Phase: [from roadmap]. Last commit: [hash — msg].
Progress: [from PROGRESS.md]. Skills loaded: [list].
```

Do NOT start coding before seeing this brief. If the agent starts working
without it — something is wrong (see Troubleshooting section).

### Pre‑session check (optional, from terminal)

Before opening OpenCode you can run `make start` from the terminal.
It shows `git log`, checks `PROGRESS.md` freshness, verifies the
`.session-ended` guard, and prints a summary — so you have context
before the agent session begins. This is optional.

### What if you already wrote a question?

The agent runs the Session Start sequence silently before responding.
You'll get the brief before any code changes.

## 5. Session Lifecycle

A session follows a strict cycle:

```
Start → Work → Commit → (DoD) → Push → (Session End)
```

### Start

Run `Start`. Agent runs 8-step sequence, outputs session brief.
You describe what you need.

### Work

Agent reads relevant docs, loads skills, implements changes.
You review, give feedback, request fixes.
Each change is one step — no multiple simultaneous changes.

### Commit

When a unit of work is complete:

```
git add .
git commit -m "type(scope): description"
```

The commit MUST NOT happen without your explicit approval.
The agent asks: "Ready to commit?"

The pre‑commit hook automatically runs `make dod` before every `git commit` —
no command needed. If any of the 6 checks fail, the commit is blocked.

### Definition of Done

After commit, BEFORE push, the agent runs the 6-step DoD checklist:
1. PROGRESS.md updated
2. Architecture docs checked/updated
3. JSDoc added for new code
4. Tests run and pass
5. roadmap.md checked
6. Safety check (no Russian in files, no forbidden files touched)

Most checks are automated via `make dod` (pre‑commit hook): tests,
Cyrillic scan, docs matrix (SIGPIPE-safe, uses `sed` instead of `head`). The agent handles the rest manually.
Only after all steps pass does the agent report "done".

### Push

You explicitly say "push" or the agent asks:
"Ready to push to remote?"
You confirm. The agent pushes.

### Session End

After push, the agent runs Session End Protocol:
1. Check if docs are behind code
2. Update PROGRESS.md with session summary
3. Create `.session-ended` guard file
4. Output: what was done, what's next, docs status

If you exit without `make session-end` (or `end / done / Ende` inside
OpenCode), the `.session-ended` guard is missing. Next `make start` will
show a warning.

### Commit-and-push combined command

When you say "commit and push", the agent:
1. Creates the commit
2. Runs full DoD
3. Only after DoD is verified — runs push

This prevents the DoD from being skipped.

### Important

If you exit the session without pushing — no Session End runs.
The progress update and docs check will happen at the next session start.
This is intentional: push is the marker of a completed session.

Still, run `make session-end` (or `end / done / Ende`) even without a push —
it stores the `.session-ended` guard so the next session knows the last one
closed cleanly.

## 6. Definition of Done

The DoD is a mandatory 7-step checklist that runs EVERY time the agent says
"done", "ready", or "finished". It prevents unfinished work from being reported
as complete.

### STEP 0 — Session Scan

Before anything, the agent scrolls through the entire conversation window
and lists everything that was done this session:
- Files created or modified
- Collections or schema changes
- New components, routes, utilities
- Any other change

Then runs `git log --oneline origin/main..HEAD` to verify.

This list is the input for all subsequent steps.

### STEP 1 — Update PROGRESS.md

Completed items go to "Current status".
New bugs or issues go to "Known issues".
Next steps go to "Next session — plan".
Git log is appended.

### STEP 2 — Check architecture docs

For each changed item — is there a matching doc?
- Yes → update it
- No → if significant (new feature, new collection, new service), create one
- CSS tweaks and typo fixes are exempt

### STEP 3 — JSDoc

Any new composable, module, server route, or utility function gets JSDoc.
Not optional.

### STEP 4 — Run tests

If the project has tests — they must pass before push.
If a new feature was added — at least one test must exist.
If no test suite exists — skip this step.

### STEP 5 — Check roadmap

If the current phase is fully complete → mark with ✅ and date.
If any checkbox changed → update the file.

### STEP 5b — Skill feedback

If any skill behaved unexpectedly or missed an important step — note in `memory/YYYY-MM-DD.md` what happened and what behavior was expected. Human decides whether to update SKILL.md. Do not touch SKILL.md files yourself.

### STEP 6 — Safety check

Two checks:
- No Russian text in project files (English-Only Policy)
- No forbidden files modified (`.env`, `docker-compose.yml`, lock files)

Only after all 7 steps confirm — the agent says "done".

## 7. Hard Limits & Safety Gates

### Hard Limits — destructive actions regardless of project

The agent must NEVER do these without explicit user confirmation, in any project:

- `git push` / `git push --force`
- `rm -rf` / deleting directories
- Modifying `.env.production`
- Any actions outside the current project
- Running scripts from external sources (`curl | sh`)

### Safety Gates — project-level configs and infrastructure

The tool approval dialog must always be set to "once", never "always".

### Full gate table

| Action | Why it's gated |
|--------|---------------|
| Modifying `docker-compose.yml` | Can destroy entire infrastructure |
| Modifying any `.env` file | Contains secrets, tokens, passwords |
| Deleting collections or migrations | Irreversible data loss |
| Running `git push` | Implicit production deploy |
| Deleting files from `docs/` or `notes/` | Loss of project documentation |
| Changing permissions for any role | Risk of privilege escalation |
| Running deployment scripts | Needs approval before execution |
| Connecting to remote servers | External access requires confirmation |
| Opening browser sessions or webhooks | Unexpected side effects |
| Modifying framework config files | Core project settings |
| Running database migrations | Schema changes |
| Installing new dependencies | Changes project requirements |
| Modifying AGENTS.md | Changes agent's own rules — must be transparent |

### Why so many gates?

Every gate exists because it caused a real problem in production:
- A Docker config change caused a day-long outage
- An unrestricted `directus_users` permission exposed user data
- A service worker config change broke PWA builds
- An agent modified its own AGENTS.md without the developer noticing

### What the agent can do without asking

- Create and edit source files
- Add files to `docs/`
- Update `PROGRESS.md` and `roadmap.md`
- Read any project files
- Create new collections or fields (NOT delete)
- Add JSDoc comments

## 8. How to Initialize a Project

Three Makefile commands covering different scenarios.

### New project — interview + documentation

```bash
make init PROJECT=/path/to/new-project
```

This runs `init-project.sh` which:
1. Copies template documentation (`docs/`, `AGENTS.md`, `HARNESS.md`, `MEMORY.md`, `PLAN.md`, `PROGRESS.md`, `memory/`) into the project
2. Opens OpenCode TUI automatically with `--prompt` flag
3. The `agent-new-project` skill interviews you and generates docs

The interview (9 questions, one at a time):
- Project name and purpose
- Tech stack (framework, backend, database, deployment)
- Team size
- Stage (MVP vs production-critical)
- External integrations (APIs, payments, auth providers)
- Sensitive data (affects security priority)
- Deployment target
- Design system needs
- Project plan preference

Generated files (each shown as draft, confirmed one at a time):
- `AGENTS.md`, `ARCHITECTURE.md`, `CONTEXT.md`, `roadmap.md`, `skills-cheatsheet.md`
- `PROGRESS.md`, `MEMORY.md`, `PLAN.md`, `HARNESS.md` — session continuity, experience, task planning, safety context
- `memory/` folder — per-session workaround notes
- `docs/specs/phase-1.md` (if project plan requested)
- `docs/design.md` — user provides manually, not auto-generated
- `docs/plan-main.md` — user fills in vision document

### Existing project — analyze first, then documentation

```bash
make init-adopt PROJECT=/path/to/adopt-project
```

This runs `init-adopt.sh` which:
1. Opens OpenCode TUI in your project with `--prompt` flag
2. The `agent-adopt` skill runs `agent-analyze` first to map the codebase,
   then fills knowledge gaps via interview, then generates missing docs

### Analyze only — audit, no modifications

```bash
make analyze PROJECT=/path/to/project
```

Opens OpenCode in the project with `--prompt` flag and automatically starts the `agent-analyze` skill.

The skill runs 4 audits in sequence:
1. Codebase health check — system map, duplication, priorities
2. Zoom-out — architecture explanation in plain language
3. Security review — auth, API, secrets vulnerabilities
4. Premortem — top 5 risks

Results saved to `docs/audits/YYYY-MM-DD-analysis.md`. No source files modified.

## 9. Troubleshooting

### Agent skipped Session Start

If the agent starts working without running the 8-step sequence:

Stop and ask:
```
Run Session Start sequence first.
```

This resets the agent to the correct entry point. The rules in AGENTS.md
mandate Session Start on every first message, so the agent should comply.

### Agent modified something without asking

Check the Safety Gates table. If the action should have required confirmation
but didn't:

```
You modified X without asking. That requires my confirmation.
Roll back the change and ask before making it.
```

Then verify the rollback with `git diff` or `git status`.

### Tests failed during DoD

The agent should report which tests failed and fix them before reporting done.
If the agent says "done" without fixing:

```
Definition of Done STEP 4 — tests failed. Fix them before reporting done.
```

### Docs fell behind code

The agent checks this automatically after every response (silently):
```
git log --oneline -- docs/ | head -1
git log --oneline | head -1
```

If docs are more than 5 commits behind, the agent asks if you want a docs update.
If the agent didn't ask:

```
Are docs up to date with recent changes?
```

### Agent ignored a rule

If you see behavior that violates AGENTS.md:

```
You just violated [specific rule]. Check global AGENTS.md section [X]
and follow it from now on.
```

The agent reads the file fresh when instructed. It does not have persistent
memory between sessions.

### Session context ran too long

If the agent starts forgetting earlier parts of the conversation:

```
Run handoff skill — pack context and continue.
```

The handoff skill creates a document summarizing the session so far,
which the agent can use in a fresh context.

### `opencode run` command doesn't work

The `init-project.sh` and `init-adopt.sh` scripts use `opencode run "..."`.
If this fails:

1. Check that opencode is installed: `which opencode`
2. Check version: `opencode --version`
3. Run the command manually: `Load ~/.config/opencode/skills/harness-init/agent-new-project.md`

The `run` command was added in OpenCode 1.x. If you're on an older version,
update: `npm install -g opencode-ai`

### Agent modified AGENTS.md without confirmation

This is a critical violation. AGENTS.md is the agent's own rulebook.
It MUST NOT be changed without the developer knowing.

```
Revert the AGENTS.md change. You must never modify your own rules
without my explicit confirmation.
```

## 10. Windows / Cross-Platform

### Short version

**Windows requires WSL2 (Windows Subsystem for Linux) for bash scripts.**
The Makefile, `install.sh`, and init scripts are all bash-based.
They do not run on native Windows Command Prompt or PowerShell.

### Step-by-step WSL2 setup

**Step 1 — Install WSL2**

Open PowerShell as Administrator:

```powershell
wsl --install
```

This installs WSL2 with Ubuntu by default. Restart when prompted.

**Step 2 — Set up Node.js in WSL**

After restart, open Ubuntu from your Start menu:

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
source ~/.bashrc
nvm install 20
```

**Step 3 — Install OpenCode and the harness**

```bash
git clone git@github.com:Dimas53/opencode-harness.git
cd opencode-harness
make setup
```

All commands run inside WSL.

**Step 4 — Access your project files**

Your Windows files are at `/mnt/c/Users/YourName/` inside WSL.
For better performance, keep projects inside WSL's Linux filesystem (`~/projects/`)
rather than on `/mnt/c/`.

**Step 5 — OpenCode auth**

```bash
opencode auth login
```

You'll get a URL to open in your Windows browser for authentication.
This works cross-platform — the browser opens in Windows normally.

### If WSL is not available

If you cannot install WSL2 (restricted machine, no admin rights),
follow the manual steps below instead of using Make commands.

### Manual installation (no Make)

```bash
# 1. Install Node.js (from https://nodejs.org)
# 2. Install OpenCode
npm install -g opencode-ai

# 3. Install MCP servers
npm install -g @modelcontextprotocol/server-filesystem
npm install -g @playwright/mcp
npx playwright install

# 4. Copy global files from the cloned repo
mkdir -p ~/.config/opencode/skills
cp global/AGENTS.md ~/.config/opencode/AGENTS.md
cp global/opencode-config.example.jsonc ~/.config/opencode/opencode.jsonc
# Edit opencode.jsonc — replace /YOUR/HOME/PATH and YOUR_DIRECTUS_TOKEN
cp -r global/skills/* ~/.config/opencode/skills/
```

### Manual project initialization (no Make)

```bash
# New project
mkdir -p /path/to/project/docs
mkdir -p /path/to/project/memory
cp -r templates/docs/* /path/to/project/docs/
cp templates/HARNESS.md /path/to/project/
cp templates/MEMORY.md /path/to/project/
cp templates/PLAN.md /path/to/project/
cp templates/PROGRESS.md /path/to/project/
cd /path/to/project
Load ~/.config/opencode/skills/harness-init/agent-new-project.md

# Existing project
mkdir -p /path/to/project/docs
mkdir -p /path/to/project/memory
cp -r templates/docs/* /path/to/project/docs/
cp templates/HARNESS.md /path/to/project/
cp templates/MEMORY.md /path/to/project/
cp templates/PLAN.md /path/to/project/
cp templates/PROGRESS.md /path/to/project/
cd /path/to/project
Load ~/.config/opencode/skills/harness-init/agent-adopt.md
```

### Commands that differ on Windows (even in WSL)

| Command | Notes |
|---------|-------|
| `opencode run` | Works the same |
| `npx playwright install` | Downloads Chromium into WSL — works |
| `opencode plugin add` | Works the same |
| `npm install -g` | Works the same |
| `make setup` | Requires `make` — install via `sudo apt install make` |

### macOS vs Linux vs WSL

The harness was built and tested on macOS. Linux (Ubuntu, Debian) and WSL2
are fully compatible. Native Windows (PowerShell) and other Linux distros
may require adjustments.

If you encounter issues, run the manual steps instead of Make commands,
and report the problem so the harness can be updated.
